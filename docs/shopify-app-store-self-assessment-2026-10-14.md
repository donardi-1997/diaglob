# DIAGLOB — autoevaluación Shopify App Store

**Fecha:** 2026-10-14  
**Base evaluada:** árbol local del repositorio en esta fecha; `shopify.app.toml` declara una configuración reconstruida. La guía oficial de la habilidad `shopify` se siguió y Shopify CLI 4.9.3 descargó en vivo `app-store-ai-self-review-requirements`.  
**Alcance:** revisión estática de código, configuración y evidencias documentales; no se accedió a Partner/Dev Dashboard, tiendas, secretos, datos personales ni endpoints privados. No se hicieron cambios de código/configuración, despliegues ni envíos a Shopify.  
**Convención:** **PASS** = evidencia local favorable; **FAIL** = contradicción o bloqueo visible; **NEEDS REVIEW** = no demostrable localmente o depende de revisión externa. PASS no implica aprobación oficial.

## Resumen ejecutivo

**Estado: NO LISTA PARA ENVÍO.** Hay bloqueos P0 de privacidad, sesión incrustada, divergencia de permisos y billing público/listing. La configuración declara los tres webhooks obligatorios y existe una recepción autenticada, durable y deduplicada; sin embargo, la aplicación aún no entrega solicitudes de acceso ni ejecuta borrado efectivo. Los documentos recientes también dicen que falta una entrega Shopify válida de producción y una confirmación viva de suscripciones en la versión activa. No se debe presentar la recepción HTTP como cumplimiento de la solicitud.

### Prioridades

- **P0 — resolver antes de enviar:** (1) implementar y evidenciar fulfillment real de acceso, redacción de cliente y redacción de tienda, incluidos sistemas locales, contenido de IA, procesadores y backups; (2) confirmar en la versión activa los tres topics y endpoint HTTPS y probar entrega válida aislada; (3) alinear scopes entre TOML, OAuth y grants, explicar necesidad de `read_customers`, `read_orders`, `write_orders` y eliminar/restringir permisos no necesarios; (4) hacer que toda la UI incrustada funcione con autenticación Shopify sin depender de Cognito/localStorage en iframe; (5) terminar Shopify App Pricing para instalaciones App Store y demostrar aceptación, rechazo, reinstalación y cambios de plan; (6) completar los campos del listing, cuenta de prueba y screencast.
- **P1 — resolver antes de aprobación o declarar claramente:** revisar todas las mutaciones de creación de pedidos/manuales frente a la regla de Shopify Checkout; validar instalación/reinstalación en tienda de revisión, navegación y estados de error; verificar consentimiento de Protected Customer Data y campos concretos; comprobar comportamiento real de expiración/renovación de tokens y aislamiento de roles/tiendas; validar URLs legales/support y TLS desde el exterior.
- **P2 — mejora posterior:** reemplazar módulos “próximamente” u ocultarlos de la experiencia de revisión, consolidar navegación con interfaz embebida coherente, y mantener vigilancia de cambios de versión API y dependencias. No declarar funciones fuera del flujo Shopify incrustado como parte de la experiencia lista para revisión sin QA real.

### Bloqueos de envío detectados

1. **Privacidad (P0):** el procesador devuelve expresamente `fulfillment_complete: false`; las tareas son revisión manual bloqueada, no exportación/borrado efectivo. La política, retención y cobertura de terceros/backups no está cerrada.
2. **Auth de app incrustada (P0):** App Bridge ID token está presente, pero para datos de negocio se exige además login de contraseña Cognito. El panel DIAGLOB almacena access/ID/refresh tokens en `localStorage`, contrario al requisito Shopify para funcionar con cookies de terceros bloqueadas/incógnito.
3. **Scopes/protected data (P0):** el TOML del repo no coincide con `SHOPIFY_SCOPES`; la evidencia del Dashboard activo ya mostró una tercera lista diferente. No está acreditado el grant instalado ni la aprobación de datos protegidos. `write_orders` sí tiene uso aparente (crear pedido), pero expone una operación que necesita revisión de política Checkout.
4. **Monetización/listing (P0):** el campo de Partner para planes seguía bloqueado/no guardado en la última evidencia documental; no hay cuenta de reviewer funcional ni screencast. El workspace de billing local es en gran medida verificación/reconciliación y no prueba la ruta completa de compra pública.
5. **Integración de checkout (P1 con potencial de P0):** hay mutaciones para crear pedidos desde el backend con información de comprador y dirección. Debe determinarse que esos flujos son exclusivamente administrativos/COD permitidos y no una vía que eluda checkout. No es posible inferirlo solo del endpoint.
